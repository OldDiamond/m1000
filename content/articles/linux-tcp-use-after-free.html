Long before a web application checks a password or validates a parameter, its host has already processed the packets that establish the connection. That work is easy to overlook during an application assessment: it happens beneath the routes, responses and access logs that usually guide the investigation.

CVE-2026-98432 brings that lower layer into focus. A race in Linux’s IPv4 TCP handling can leave one execution path using memory that another has released. Understanding the finding means following that shared state through the handshake, then separating the underlying defect from the conditions demonstrated in an exploit.

Start with the advisory’s actual scope

AWS’s advisory places the vulnerability in the IPv4 TCP handshake path of unpatched kernels from Linux 4.4 onward. Relevant packets carry IP options. Possible outcomes include a kernel crash, disclosure of kernel memory and memory corruption. Its November 2 update describes demonstrated remote code execution against an MPTCP listener and says AWS had no evidence of exploitation at that time.

Those statements answer different questions: what the defect can affect, what researchers demonstrated, and what a provider observed. Keep those distinctions in an assessment. A kernel version string alone is also insufficient evidence of exposure, because a distribution may have backported the repair into its own package stream.

Follow the state through the TCP handshake

A simplified TCP handshake begins with SYN, continues with the server’s SYN-ACK, and completes with an acknowledgment. While the connection is incomplete, Linux maintains temporary request state. An established connection needs a child socket with the state required to carry subsequent traffic. Different execution contexts can work on those objects at overlapping times.

IPv4 options are fields in the IP header. They sit outside HTTP and can introduce additional state that the networking code must retain and eventually release. That lifetime has to remain valid through retransmissions, connection teardown and ownership changes. Retransmission is ordinary network behavior; the challenge is keeping shared state safe while processing it.

Why the ownership handover becomes unsafe

A use-after-free occurs when software accesses memory after its allocation has been released. The pointer can still contain a plausible address even though the old object no longer owns that storage. If the allocator reuses it, the same address now refers to something else. Reads can expose unintended data, and writes can corrupt another object.

Akamai’s patch analysis describes IPv4 option state moving from a request socket to the established child socket without a copy. Concurrent retransmission processing can still be reading that state when child-socket destruction releases it. The reader relies on read-copy-update, or RCU: a coordination mechanism whose memory-reclamation rules must be respected.

The repair defers freeing until the relevant RCU readers finish. The analysis also identifies a related request-socket migration path. Conceptually, the broken lifetime looks like this; this diagram is explanatory, not an exploit sequence:

Reader:    obtain shared state ---- continue reading ---- finish
Owner:                 release state
Required:                              defer reclamation until readers finish

The race appears when a lifetime decision and a concurrent read disagree about whether an object still exists. Reviewing only the cleanup function can miss that disagreement. The useful question is which readers remain active when ownership changes, and what synchronization guarantees protect their final access.

Separate the demonstrated exploit from broader exposure

Anthropic’s original research disclosure reports unauthenticated command execution as root against a server with a multipath TCP listener. Its account describes a memory-disclosure stage followed by control-flow manipulation. I attribute that demonstration to its researchers; it does not establish reliable exploitation against every kernel build, networking setup or ordinary listener.

Remote code execution means a remote party can cause a system to execute attacker-selected code. Kernel execution is especially consequential because the kernel enforces boundaries between processes. That potential impact explains the urgency, but a crash, a failed handshake or an unusual packet is not evidence that an attacker reached code execution.

The demonstrated MPTCP prerequisite should guide prioritization, not become a reason to ignore other affected hosts. Ubuntu’s November 2 guidance explicitly warns that the underlying flaw is not confined to MPTCP and recommends security updates rather than treating MPTCP changes as a complete solution.

Build an exposure finding without racing a production kernel

Begin with the running kernel, distribution release, applicable vendor advisory, patch history and listener configuration. Then establish where TCP terminates. A proxy that accepts a client connection and creates a new backend connection presents a different path from a device that forwards packets. Confirm the topology with the owner rather than inferring it from an HTTP banner.

A read-only inventory check can establish the kernel currently in use:

uname -r

Keep that result separate from the installed package inventory. A fixed kernel on disk does not prove that the machine has booted into it. The same distinction applies to containers: updating a container’s user-space packages does not establish the patch state of the host kernel.

An exploit attempt is unnecessary for many assessment findings and can put availability at risk. If reproduction is required, define a separate authorized lab test with recovery arrangements. For production, a documented chain from vendor advisory to package status, running kernel and reachable service can support a precise, actionable report.

Investigate symptoms, then verify the repair

Unexpected kernel faults, reboots and changes in connection-failure patterns deserve investigation alongside existing network telemetry. These symptoms are nonspecific: ordinary faults can produce them too. Application logs may add context, but a defect reached during connection establishment may leave no corresponding application request.

Preserve relevant kernel logs, crash information and available packet metadata before rotation removes them. Build a timeline of exposure, restarts and package changes. If there is evidence of compromise, include incident response in the remediation plan; installing a patch cannot establish what happened before it was applied.

AWS documents fixed Amazon Linux kernel packages and instructs customers to update and reboot. Distribution rollout differs: Ubuntu’s November 2 notice distinguished proposed updates from generally released updates. Follow the applicable vendor’s current supported procedure rather than copying another distribution’s version or enabling a testing repository without operational review.

Close the finding with the advisory identifier, installed package, kernel running after restart, relevant service boundaries and verification date. That evidence is more useful than an unqualified “Linux is vulnerable” statement. The lasting assessment lesson is to follow the application’s dependencies all the way down to the code that accepts its connections.
