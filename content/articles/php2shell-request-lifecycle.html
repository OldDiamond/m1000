A PHP application can have careful input validation and a well-protected login page while still relying on an unsafe runtime. Before the application starts, PHP may already be parsing input and preparing memory. After it finishes, the worker must release that memory without leaving references for the next request to encounter.

PHP2Shell concerns failures at those boundaries. CVE-2026-109618 and CVE-2026-109619 turn out-of-memory handling and retained worker state into potential routes to remote code execution. For a web penetration tester, they are a reason to ask what happens before the first application instruction and after the last one.

Establish the affected runtime and execution model

The PHP project’s October 21 security announcement identifies fixed releases 8.2.35, 8.3.36, 8.4.27 and 8.5.12. It urges updates across web-serving deployments, including PHP-FPM, Apache mod_php, php-cgi, FrankenPHP and LiteSpeed. It singles out mod_php as the highest risk, with demonstrated unauthenticated exploitation before application code runs.

The advisories distinguish demonstrated cases from paths that require additional conditions. Application behavior, startup configuration and requests reaching the same worker can all matter. Identify the hosting interface and worker model before carrying an exploitability conclusion from one deployment into another.

Follow a request through startup, execution and shutdown

PHP’s hosting interface connects the web server to the language engine. Configuration and extensions take part in startup, request data is prepared, the application executes, and shutdown releases resources owned by that request. Each phase has assumptions about which objects exist and which state is safe to inspect.

Reusing a worker avoids starting a fresh process for every visitor. It also means the process can outlive the data it handled for an earlier request. Cleanup must remove references to released request memory before any later operation can reach them. An address left in a persistent field does not keep the old allocation valid.

Worker begins request A
    → prepare input → execute application → clean up request A
    → reset request-owned references
Worker begins request B

This is a different assessment layer from an unsafe SQL query or missing authorization check. Those defects belong to application behavior. A runtime flaw breaks guarantees the application depends on. Application validation remains important, but it cannot reliably correct an engine failure that happens during earlier parsing or later cleanup.

CVE-2026-109618: an allocation failure leaves unfinished state

PHP’s out-of-memory advisory explains that an allocation failure can cause a nonlocal exit using longjmp(). If request memory has become reachable before initialization finishes, that exit can leave invalid state for shutdown to consume. Memory exhaustion is therefore not only an availability event: unsafe recovery can create a memory-corruption opportunity.

Memory corruption is a violation of the intended layout, ownership or lifetime of stored data. Its consequences depend on what later code does with the damaged values. If an attacker can turn that influence into execution of chosen code through a remote request, the result is RCE. The existence of a memory error alone does not establish a working exploit.

The advisory validates complete RCE against mod_php. It distinguishes FPM’s behavior when request startup fails: the child exits, preventing that exact cleanup sequence. Other application-dependent paths remain relevant. Its patch changes how OOM is handled so that incomplete state does not reach unsafe shutdown processing. This distinction is a reason to read the advisory, not a reason to classify every FPM deployment as safe.

CVE-2026-109619: a reused worker consumes a stale reference

The stale-global-state advisory describes a different lifetime failure: a worker retains a reference to request-owned memory after that memory has been freed. A later operation can consume the reference before normal initialization replaces it. This is a use-after-free, where the address survives but the object’s ownership does not.

The advisory models a producing operation, an interruption or missed reset, and a later consuming operation in the same worker. It documents confirmed fatal-backtrace and session lifecycle cases, while treating other paths as conditional. Its validated FPM session path requires suitable application execution after successful startup. Worker reuse, configuration and reachable application behavior therefore matter to a precise finding.

Suppressing an error message does not establish that the underlying operation was avoided. The advisory explains that stale state may be accessed before PHP decides whether to display or log a diagnostic. Assess the operation and its timing rather than using a quiet response as evidence that the memory lifecycle is safe.

Why a login page may be too late in the lifecycle

An authentication check can protect operations that occur after it. If request startup reaches vulnerable runtime code first, the application has not yet had an opportunity to reject the caller. This is why an authenticated interface can still require urgent runtime patching, even when its application-level access controls work as intended.

There is also evidence beyond laboratory demonstrations: Unit 42’s October 29 update reports active exploitation against internet-exposed PAN-OS management interfaces and verification of an exploit chain involving a separate kernel privilege-escalation flaw. This is a vendor-specific observation; it should not be generalized into a claim that every PHP deployment has been compromised or that PHP execution automatically grants root.

Verify the runtime that actually serves HTTP

Collect the PHP branch, package provenance, hosting interface, worker configuration and update history with the owner. A command-line php -v result can help, but the CLI binary may differ from the service handling web traffic. Use an existing administrative inventory or a controlled local check instead of publishing a diagnostic page.

Match the active service to the applicable vendor package advisory. A backported repair can leave a version string that looks old, while an updated binary on disk can coexist with older running workers. Check each in-scope pool, container image and management interface, then record which process or image is actually serving requests.

Upgrade to a supported fixed or later release and restart or replace affected workers. PHP 8.1 and older are outside upstream security support; the PHP project notes vendor backports and limited source-backports, but these do not amount to renewed upstream support. An upgrade plan should address that maintenance risk as well as the immediate CVEs.

Investigate evidence without treating symptoms as signatures

Correlate OOM events, worker exits, crashes and unexpected child processes with existing request logs. Review changes to writable application directories and suspected access to service credentials. Each is a lead to investigate, rather than a definitive PHP2Shell indicator. Preserve relevant evidence before worker recycling or log rotation removes it.

For systems awaiting a patch, use the current vendor’s deployment-specific guidance. Bound decoded input at the frontend and restrict unnecessary public access, but do not treat a WAF or a memory setting as a complete fix. PHP’s later October 23 notice adds a separate, unusually configured session-upload-progress caveat; staying current with that guidance matters even after an initial emergency upgrade.

Close the finding with evidence of fixed workers

A useful assessment produces a verified runtime inventory, a clear account of the applicable conditions and evidence that fixed workers now serve the affected traffic. It records which exploit paths were demonstrated by the cited researchers and which conditions remain unverified in the assessed environment.

The practical lesson is to extend web testing across the whole request lifecycle. Startup, failure handling and worker reuse are part of the application’s security foundation. Verifying those dependencies gives the owner a stronger result than an application-only checklist or an unqualified version alert.
